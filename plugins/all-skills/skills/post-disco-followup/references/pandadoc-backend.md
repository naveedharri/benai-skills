# PandaDoc backend

How to create the proposal draft in PandaDoc. Used only when `proposal.backend` is `pandadoc`. The template id, token names, pricing table name, and role come from `config/pandadoc.md`, which the setup wizard generated by reading your real template. Use the names in config, not the examples here.

## Two transports

`config/pandadoc.md` sets `transport`:

- **`connector`** (recommended): the native PandaDoc MCP, available in Claude Desktop and in Claude Code when the connector is added. No API key to manage. Tools: `mcp__*__create_document`, `mcp__*__get_document_status`, `mcp__*__get_document_details`, `mcp__*__get_template`, `mcp__*__delete_document`.
- **`api`**: direct REST to `https://api.pandadoc.com/public/v1`, header `Authorization: API-Key <value of the env var named in config>`. Works only where you can make HTTP calls (Claude Code with a shell). This is what fails in Cowork and plain Claude Desktop.

Pick the transport the environment supports. If both are available, prefer the connector.

## Document payload (same fields either way)

- name: `<Legal Company Name> - <program_name> Proposal`
- template: the `template_id` from config (`template_uuid` in REST, `template_id` in the connector)
- recipients: one, with the configured `role_name`, `signing_order: 1`, prospect email/first/last
- tokens: one entry per token, `{ "name": "<exact name>", "value": "<filled>" }`
- pricing_tables: name matching `pricing_table.name` exactly, one row, `data` keys lowercase `name`/`price`/`qty`, price/line item from `config/offer.md`

## Filling tokens (read this, it caused a real bug in testing)

The introspection call returns ALL tokens DEFINED in the template, which is often MORE than are visibly placed (for example 49 defined vs 34 placed), and can include a blank-named token (`""`).

Rules:
- Map and fill EVERY named token you can. Do not fill only the ones you recognize, that leaves real slots blank.
- Skip any token whose name is empty.
- Extra tokens you pass that the template has no slot for are silently ignored, which is fine. Over-filling is safe, under-filling is not.

Formatting inside tokens: bullets are plain-text `- item\n- item` (no markdown). Single-sentence fields stay prose. No em dashes. Do not repeat any label that is static in the template (the `static_labels` list in config).

## Verify after creation (do not skip)

1. Poll status until `document.draft` (connector: `get_document_status`; REST: `GET /documents/{id}`).
2. Get details (connector: `get_document_details`; REST: `GET /documents/{id}/details`) and confirm every token populated, no empty brackets, pricing correct, recipient assigned.
3. Capture the document id.

## The draft-link limitation (important, confirmed in testing)

A document in `document.draft` status has NO prospect-facing link:
- The details response has no `view_url`.
- `POST /documents/{id}/session` returns 400: "Cannot create session ID for a document in document.draft status."

So you cannot put a working proposal link in the email at draft stage. Do NOT fabricate one and do NOT use the owner app url (the prospect cannot open it). Instead:
- Leave a clearly marked placeholder in the email draft (see `references/email-format.md`).
- In the confirmation, tell the user the link is created when they send or share the document from PandaDoc, and to paste it into the email draft before sending the email.

If the user wants a real link without sending, the only path is to move the document out of draft (send it, or share it from the PandaDoc UI), which is a deliberate user action, not something this skill does.

## Sandbox vs production

If `key_environment` in config is `sandbox`, documents are watermarked and titled with a `[DEV]` prefix. They are test documents, not real client proposals. Say so in the confirmation so nobody mistakes a sandbox draft for a live one.

## Never
- Do NOT call send (`POST /documents/{id}/send` or the connector send tool). Draft only.
- "Payer" is not an API role, it is a UI billing toggle.
- Do NOT uppercase pricing row keys.
